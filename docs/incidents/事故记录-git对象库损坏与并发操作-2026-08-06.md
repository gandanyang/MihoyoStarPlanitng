## 二、根因分析

### 直接原因（多因素叠加）

1. **多 AI 会话并发操作同一 git 仓库**（WorkBuddy / TRAE / Codex 都在动），commit/ref 更新互相竞争
2. **中断的 gc/repack**：pack 目录的 tmp_pack 说明有 gc 启动但未完成（可能被另一会话的写操作打断），导致**已提交的 commit 对象被卷入损坏的打包流程而丢失**
3. **历史累积损坏**：fsck 早就报告多个 broken link（历史孤儿对象），说明对象库此前就不完全健康，为本次事故埋下隐患

### 触发链条

```
历史孤儿对象（弱健康）
  + 多会话并发 git 写操作（竞争）
  + 中断的 gc（打包半途）
  → 新 commit 的松散对象未落盘/被清 → ref 指向不存在对象
  → HEAD bad object → 仓库不可写
```

### 为何没能更早发现

- 单 blob 缺失（20:20）被当成一次性问题修复，未意识到是**系统性损坏的前兆**
- 未检查是否有其他会话正在操作仓库（多 AI 协作下这是关键盲区）

## 三、影响与数据保全

### 损失

- ⚠️ **git 历史重写**：恢复方式为重打根提交，**所有历史 commit 被折叠为一个根提交**（commit 粒度历史丢失，工作区内容完整保留）
- 历史 refs（tags/远程分支）指向旧对象，fsck 仍报失效（自然现象，不影响主分支）
- 两个临时 esc 探针（probe-esc-repro-tmp / probe-esc-v2-tmp）在工作区被删除（他人操作，属清理）

### 保全（重要）

## 四、教训与预防措施

### 对多 AI 协作的约束（最重要）

1. **同一仓库原则上只允许一个 AI 会话执行 git 写操作**；并行工作时应明确"提交权"归属
2. 发现 `invalid object` / `bad object HEAD` / fsck broken link 增多 → **立即停手**，报告协调，不得自行 `gc`/`repack`/`reset`
3. 提交前先 `git log -1` + `git status` 确认无其他会话写入痕迹

### 对 git 仓库健康

4. **定期 `git fsck --full`**（每周或每批提交后），broken link 增多是危险信号
5. 对象库异常时**不要跑 `git gc`**（gc 会重写对象，与并发写竞争可能加剧损坏）；优先 `git hash-object -w` 精确补对象或整体迁移
6. 重要里程碑后考虑**推送远端备份**（origin/main 也失效过，本地单点风险高）

### 对工具使用

7. 临时诊断脚本（`_fix_missing_blobs.mjs` 等）用完即删，不留在工作区
8. 多 AI 协作项目应约定：**大文件/二进制（如语音、图片）的提交时机**，避免并发 add 大文件时触发 gc
